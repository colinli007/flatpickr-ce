## 请回答

每条结论都要带你实际读到的 `文件:行号`，支撑结论的事实要写依据（查了哪些调用方、在哪一行、跑了哪个测试）；没查证的推断要明说是推断。

1. **根因**：根因陈述对不对？这次修复打在根因上，还是只压住了症状？仓库里还有没有同一个根因的其他出现点没修（另一种 mode、另一个插件、另一条输入路径）？
2. **信号是否最精确**：这个问题本质上是对什么的反馈？系统里对它已有的最精确信号是什么？修法用的是不是那个信号？出现以下征兆要明确指出：靠前后状态 diff 猜意图、新加 flag 区分场景、在共用路径上加特判、用 setTimeout 绕时序。
3. **PR 处理**（输入是 PR 时）：「原样合并 / 重写 / 不合并」这个选择对不对？重写时，和 PR 原写法比是不是真的更好，PR 里有没有该保留却丢掉的东西（测试、边界处理）？
4. **每个新增的分支 / 状态 / 事件绑定 / 字段**：分别防的是哪个具体场景？说不清的就是多余的。反过来，修复删掉的东西，当初防的是什么，删了会不会回归？
5. **影响面与回归**：改动点的所有调用方是否都受影响、是否都符合预期？至少考虑 single / multiple / range 三种 mode、`inline`、`static`、`allowInput`、`enableTime` / `noCalendar`、移动端原生输入、各插件。行为变化有没有在根因陈述里如实列出？
6. **测试**：新增的测试能不能在修复前失败（用 `git show HEAD:<路径>` 对照判断）？有没有覆盖第 5 项里受影响的相邻情形？
7. **与仓库既有写法是否一致、有没有冗余**：同类问题仓库别处怎么处理？有没有该一起删掉却留下的死代码、过时的注释？
